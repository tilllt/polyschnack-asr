Six independent agents reviewed the repository in parallel — one each for security, code smells and pitfalls, supply chain, uniformity, simplicity, and naming — reading the actual source rather than sampling it. Together they produced 126 verified findings across roughly 26,000 lines of Python, 8,000 lines of TypeScript, nine Dockerfiles, five compose files and two CI pipelines.

The headline: this is a capable, well-tested codebase (roughly 70 test modules, a strict-TypeScript frontend, uniform HTTP-client and logging call style) whose trust boundary has not kept pace with its feature growth. The three most serious problems are all on the same axis — endpoints that accept work from unauthenticated callers and then perform expensive, privileged, or cross-tenant operations: an unauthenticated URL-import route that hands a raw user string to yt-dlp, a transcript download route with no access check at all, and an upload de-duplication query that matches across all users and returns the other user's transcript.

The second theme is the event loop. Only six of 75 endpoints are declared async, and three of those six are precisely the ones doing multi-minute blocking work (yt-dlp, ffmpeg, a synchronous ASR call with a 3600-second timeout), so the convention is not merely inconsistent — it is inverted exactly where it costs the most. A single such request freezes the entire server for every other user.

The third is provenance: model weights are pulled from mutable HuggingFace refs with no checksum, the management script can overwrite itself from the network after only a syntax check, and Docker builds ignore every lockfile in the repository. Nothing here is exotic; all of it is fixable with bounded, local changes. See RECOMMENDATIONS.md in this folder for the ordered work plan.

By area

Security 17

Authn/authz, SSRF, injection, secrets, container posture

1 critical5 high6 medium4 low1 info

PolySchnack has a thoughtfully designed authorization core (central permissions.get_access_level with read/write/full levels, API-key rights caps, hashed API keys with expiry, an explicit SSRF validator for BYOK endpoints, a path-traversal guard in the recovery router, safe list-form subprocess calls and parameterised SQL everywhere), but that core is not applied consistently, and several ingress points bypass it entirely. The most serious issues are: an unauthenticated URL-import endpoint that hands an attacker-controlled string straight to yt-dlp (server-side request forgery into the internal Docker/ASR network plus yt-dlp argument injection, since the URL is not separated from the option list by '--'), a transcript download route with no access check at all, cross-tenant transcript disclosure via global content-hash duplicate detection on upload, an OpenAI-compatible transcription proxy whose 'API key required' dependency silently accepts anonymous sessions, and a shipped dummy SESSION_SECRET in compose.oidc.yml which — because Starlette session cookies carry the is_admin flag and Fernet credential encryption is derived from the same secret — turns into admin-session forgery and decryptable stored credentials. Checked and found CLEAN: no SQL injection (SQLModel/SQLAlchemy statements are parameterised; the only f-string SQL in db._auto_migrate builds identifiers from the model metadata, never from request data); no eval/exec/os.system/shell=True/pickle; every ffmpeg/ffprobe/crispasr/aligner invocation uses list argv with non-string-interpolated parameters (durations are floats, paths are server-generated UUID names); no dangerouslySetInnerHTML, innerHTML, document.write or eval anywhere in the React frontend; the service worker never caches /api/* or /health and ignores non-GET requests; no CORS middleware is registered (so no permissive cross-origin policy) and the session cookie keeps Starlette's httponly+SameSite=lax defaults with https_only derived from BASE_URL; no SSTI (render_template is only called with static templates); API-key tokens are 32-byte urlsafe randoms stored as SHA-256 hashes and looked up by hash, with expiry enforced; recovery/restore rejects path separators and '..'; benchmark sample ids are resolved against the manifest rather than joined into a path; robots.txt plus an X-Robots-Tag middleware cover share links; and no real secrets are committed (CI uses variables, .env is gitignored).

Code Smells 23

Latent bugs: concurrency, event loop, resource leaks, correctness

2 critical7 high9 medium5 low

The webapp mixes async FastAPI handlers with fully synchronous, minutes-long work (yt-dlp, ffmpeg, blocking ASR HTTP calls with a 3600 s timeout), so a single URL import or proxy transcription freezes the entire server event loop — this is the most damaging class of defect found. A second cluster is unscoped/absent authorization: the upload duplicate check matches content hashes across all users and returns the other user's transcript, and GET /recordings/{uid}/download performs no access check at all. The threading in queue.py is sound in its locking but has two behavioural defects: workers block on a per-backend semaphore after dequeuing (head-of-line starvation across backends) and cancel() races the worker's status transition. Resource handling leaks in several places: rejected anonymous uploads leave orphan files on disk, permanently-failing preview generation makes the backfill loop re-run a 600 s ffmpeg transcode every 30 s forever, and SMTP delivery has no timeout so a worker slot can hang indefinitely. Test coverage is broad (nearly every module is exercised), so the gaps below are behavioural, not untested-code gaps.

Supply Chain 16

Dependencies, base images, model weights, CI provenance

6 high4 medium5 low1 info

PolySchnack's supply chain is held together by mutable references: every ASR model weight (~5 GB of GGUF) is pulled from HuggingFace `resolve/main` with no checksum or signature, the CrispASR binaries come from GitHub release tarballs verified by nothing, and two images compile qwen3-asr.cpp from an unpinned `git clone --recursive` of upstream HEAD. Lockfiles exist (webapp/uv.lock, approach-a/uv.lock, package-lock.json with full integrity hashes) but the Docker builds bypass all of them — the webapp image copies only pyproject.toml before `uv sync`, runs `npm install` rather than `npm ci`, and adds a floating `yt-dlp>=2026.05.29`; approach-a installs a wholly unpinned requirements.txt as root with `--break-system-packages`. Base images are tag-pinned without digests, several are `:latest` (tecnativa/docker-socket-proxy, alpine, all compose services), and node:20-slim reached EOL on 2026-04-30. The sharpest single item is `polyschnack-manage.sh selfupdate`, which overwrites the script and backends.yaml from the network with only a `bash -n` syntax check, after which URLs from that same YAML are string-interpolated into a `docker run alpine sh -c` command line.

Uniformity 24

Consistency of error handling, logging, API shapes, tooling

4 high11 medium7 low2 info

Within each layer the codebase is more consistent than its size suggests: HTTP is 100% httpx (zero requests/aiohttp), there are zero bare `except:`, logging in webapp/app is uniformly `log = logging.getLogger(__name__)` with %-style args and no f-strings, the frontend is 98% routed through src/api.ts with strict TypeScript and only 2 `any`, and 20 of 20 components follow PascalCase + named-export + interface-Props. Language is the most visible split — ~86% of frontend comments and most Python comments are German while docs/API.md and grouping.ts/format.ts are pure English, and /benchmark ships ~20 hardcoded German strings to en/pt-BR users. Infrastructure conventions drift the same way: 5 CrispASR Dockerfiles duplicate a 25-line block verbatim, only 1 of 8 Dockerfiles has a HEALTHCHECK, 1 of 4 compose services lacks one, only 3 of 9 shell scripts use `set -euo pipefail`, and CI tests on Python 3.11/3.13 while the runtime image is 3.12.

Naming 33

4 high12 medium16 low1 info

critical Security

Unauthenticated SSRF and yt-dlp argument injection in /api/recordings/from-url

webapp/app/routers/url_import.py:64

The endpoint requires no authentication (an anonymous cookie session is created on the fly) and performs no validation of the submitted URL — the project's own SSRF validator (app/llm_url.validate_llm_url, used for BYOK endpoints) is not applied here. Any internet user can make the webapp container fetch arbitrary URLs, reaching hosts only reachable from inside the compose network: http://docker-proxy:2375/containers/json, http://ps-pk-onnx:5092, http://crispr-align:5099, or cloud metadata at http://169.254.169.254/. Fetched bytes are stored as a recording the attacker owns and can download, and yt-dlp's stderr (which frequently echoes response details) is returned verbatim in the 400 detail, so this is not blind. Worse, the URL is appended as a bare positional argument with no '--' end-of-options separator, so a value beginning with '-' is parsed by yt-dlp as an option: --config-location=<path> (loads an attacker-plantable config file, which may itself contain --exec), --paths/-o (write files to arbitrary locations inside the container), --batch-file=/etc/passwd. Combined with the container running as root, this is a plausible path from an unauthenticated HTTP request to code/file-write inside the webapp container.

proc = subprocess.run(
    [
        "yt-dlp",
        "-f", "ba/b",
        "-x",
        "-o", out_template,
        "--no-playlist",
        url.strip(),
    ],

Fix Require an authenticated (non-anonymous) identity for the import; run url.strip() through validate_llm_url (extended to reject non-http(s) schemes, private/loopback/link-local IPs and DNS names resolving to them, re-checked after redirects); reject any URL not starting with 'http://' or 'https://' and pass '--' immediately before the URL so it can never be parsed as an option; add '--no-config-locations' (or --ignore-config) and a rate limit per identity; return a generic error instead of raw yt-dlp stderr.

high Code Smells

Queue worker blocks on the per-backend semaphore after dequeuing → cross-backend starvation

webapp/app/queue.py:205

A worker pops the next job from the global priority queue and only then calls sem.acquire() for that job's backend, holding the worker thread hostage. Worker count = sum of all endpoint capacities. Scenario: backends A and B, concurrency 1 each → 2 workers. Enqueue A1, A2, then B1. Worker1 takes A1 and runs it; worker2 takes A2 and blocks on A's semaphore; B1 stays in the FIFO with no free worker, so an idle backend B does nothing until A1 finishes — the ETA/position shown to the B user is pure fiction. With three queued A jobs and 2 workers, B is starved for two full transcriptions.

_, _, rec_id = self._fifo.get(timeout=1.0)
...
sem = self._semaphore_for(job.backend)
sem.acquire()

Fix Use one queue (or one worker pool) per backend, or `sem.acquire(blocking=False)` and re-queue the job when the endpoint is saturated so the worker can pick up work for another backend.

high Code Smells

cancel() races the worker: a cancelled job is still transcribed

webapp/app/queue.py:199

The worker reads the Job under the lock, then releases it and sets job.status = "processing" only after sem.acquire() returns. cancel() checks `job.status != 'queued'` under the lock. Timing: worker dequeues rec 42 and blocks on a busy semaphore; the user presses ✕; cancel() sees status still 'queued', deletes the job dict entry and resets the DB row to status='uploaded'; the semaphore frees, and the worker — holding its own `job` reference — proceeds to set_processing() and process_recording(42). The user sees a cancelled job start by itself, and if they meanwhile press transcribe again, enqueue succeeds (the dict entry is gone) so the same recording is transcribed twice concurrently, both writing update_result for the same row.

with self._lock:
    job = self._jobs.get(rec_id)
...
sem.acquire()
try:
    job.status = "processing"

Fix Claim the job atomically: inside one `with self._lock` block re-fetch it, verify it is still queued, and flip it to 'processing' before doing any blocking work; treat a missing entry as cancelled and skip.
