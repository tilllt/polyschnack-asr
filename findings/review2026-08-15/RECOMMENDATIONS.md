# PolySchnack — Recommendations by Severity

Companion to `index.html` in this folder. 126 findings from six parallel review agents
(security, code smells, supply chain, uniformity, simplicity, naming), 2026-08-15, `main` @ `d8c23b0`.

Severity totals: **3 critical · 30 high · 47 medium · 41 low · 5 info**.

Items the agents found independently and reported twice or three times are merged here and marked
*(corroborated)* — those carry the highest confidence and are usually the cheapest to fix.

---

## P0 — Critical: fix before the next deploy

### 1. `/api/recordings/from-url` is an unauthenticated SSRF and argument-injection hole *(corroborated ×3)*
`webapp/app/routers/url_import.py:64`

The route takes a raw user-supplied URL and passes it to `yt-dlp` with no authentication, no scheme or
host allow-list, and no `--` separator before the positional argument. Two distinct attacks follow.
First, SSRF: the URL can name internal hosts — the docker-socket proxy, the ASR containers, cloud
metadata endpoints — and the fetch happens from inside the container network. Second, argument
injection: a value beginning with `-` is parsed by yt-dlp as an option, so `--config-location` or
`--paths` turn the fetch into arbitrary local file reads and writes.

The same line is also the worst event-loop offender: it runs `subprocess.run(yt-dlp, timeout=600)`
twice plus ffmpeg, synchronously, inside an `async def`. One import request stalls every other user for
up to ~20 minutes and fails the health check.

**Fix:** require an authenticated identity; validate the URL against an explicit scheme
(`https` only) and a host allow-list, resolving the hostname and rejecting private, loopback and
link-local addresses — reuse the guard already written in `llm_url.py`; insert `--` before the
positional URL; and move the whole subprocess pipeline off the event loop with
`await asyncio.to_thread(...)` (or hand it to the existing job queue, which is the better fit).

### 2. OpenAI-compatible proxy blocks the event loop for up to an hour *(corroborated ×2)*
`webapp/app/routers/openai_proxy.py:141` (and `:33`)

The `async def` handler calls the synchronous `client.transcribe()`, whose httpx client is configured
with `timeout=3600`. A single long transcription freezes the entire server — every request, every
health probe — for the duration. Compounding it, `_require_identity` accepts anonymous sessions, so
`/v1/audio/transcriptions` is open compute for anyone: it bypasses both `ensure_free_only` and the
anonymous quota checks.

**Fix:** wrap the call in `asyncio.to_thread` (or make the adapter async), lower the timeout to
something bounded, and require a real API key on this route — anonymous identity should not satisfy it.

## P1 — High: schedule this sprint

### Access control

- **`GET /api/recordings/{rid}/download` has no access check at all** *(corroborated ×2)* —
  `webapp/app/routers/recordings.py:932`.
  Every sibling route calls `ensure_access`; this one does not. Transcripts stay downloadable by
  anyone who knows the uid, including after an anonymous share link has been revoked — revocation is
  therefore not actually enforced. **Fix:** add the same `ensure_access` call the neighbouring routes use.

- **Upload de-duplication leaks other users' transcripts** *(corroborated ×2)* —
  `webapp/app/routers/recordings.py:516`.
  The `content_hash` lookup is not scoped to the owner, and on a hit it returns
  `_recording_to_dict(existing)` — including `text`, `segments` and `uid`. Uploading a file you suspect
  someone else has uploaded returns their transcript. `url_import.py` already scopes this query
  correctly. **Fix:** add the owner predicate; copy the url_import query.

- **Anonymous quota is enforced after the file is written** — `webapp/app/routers/recordings.py:555`.
  The write happens first, so over-quota uploads leave orphaned files on disk, and the
  check-then-act on the `SUM` means concurrent uploads can both pass. **Fix:** check before writing,
  and enforce the sum inside the same transaction.

- **1 GB uploads are fully buffered in RAM** — `webapp/app/routers/recordings.py:506`.
  `await file.read()` materialises the whole body before the 413 check, in an async handler, and the
  ffmpeg conversion then runs on the loop. Several concurrent uploads exhaust memory.
  **Fix:** stream to a temp file in chunks, enforce the limit as bytes accumulate, and run ffmpeg off-loop.

### Secrets

- **Shipped dummy `SESSION_SECRET` signs the admin cookie** — `compose.oidc.yml:31`.
  `dummy-session-secret-change-me` is a published value, and the session cookie carries `is_admin`.
  Anyone can forge an admin session on a stock deployment — and admin can drive the Docker daemon.
  **Fix:** generate the secret at first start and fail loudly if it is still the placeholder.

- **Fernet key falls back to `sha256("dev")`** — `webapp/app/crypto.py:15`.
  That key protects BYOK LLM credentials and WebDAV passwords. **Fix:** refuse to start without a real key.

- **Random per-process `SESSION_SECRET` orphans anonymous users** — `webapp/app/main.py:219`.
  The other half of the same problem: with no secret configured, every restart silently detaches every
  anonymous user from their recordings. **Fix:** persist a generated secret.

### Queue correctness

- **Cross-backend starvation** — `webapp/app/queue.py:205`. The worker dequeues first and *then* waits
  on the per-backend semaphore, so an idle backend's jobs sit behind a busy backend's queue.
  **Fix:** select the next job whose backend has capacity, or run one worker per backend.

- **`cancel()` races the worker** — `webapp/app/queue.py:199`. A cancelled job is still transcribed, and
  a re-enqueue can run the same job twice concurrently. **Fix:** re-check cancellation under the lock
  after dequeue, and guard against double-enqueue by job state.

- **Preview backfill loops forever on unproduceable files** — `webapp/app/crud.py:134`. Rows whose
  preview always fails are re-selected every 30 s (600 s of ffmpeg each) and, because the query is
  id-ASC limit-2, they permanently block every newer row. **Fix:** record the failure and exclude
  failed rows after N attempts.

### Supply chain provenance

- **Model weights have no integrity verification** — `webapp/app/backends.yaml:71`, both
  `entrypoint.sh`. Every GGUF comes from a HuggingFace `resolve/main` URL — a mutable branch — and the
  only check is the 4-byte `GGUF` magic. Upstream can change the weights under you, silently.
  **Fix:** pin to a revision SHA and verify a recorded sha256.

- **`selfupdate` overwrites the script from the network** — `polyschnack-manage.sh:398`. It curls a
  replacement for `$0` and accepts it after only `bash -n` and a size check — no signature. Same path
  for `backends.yaml`. **Fix:** verify a signature or a pinned checksum, or drop the feature.

- **Shell injection from network-fetched YAML** — `polyschnack-manage.sh:151` and `:227`. Model URLs
  from that same downloadable YAML are string-interpolated into
  `docker run … alpine sh -c "$MODELS_SCRIPT"` (with `alpine` untagged). A hostile YAML is remote code
  execution. **Fix:** pass URLs as argv, not interpolated shell; pin the alpine tag.

- **Docker builds ignore every lockfile** — `webapp/Dockerfile:25`. Only `pyproject.toml` is copied
  before `uv sync`, and the frontend uses `npm install` rather than `npm ci`, so published images do
  not match the committed locks. **Fix:** copy `uv.lock` / use `--frozen`, and switch to `npm ci`.

- **Unpinned upstream builds** — `qwen3-asr-cpp/Dockerfile:14`, `aligner-service/Dockerfile:27` build
  `qwen3-asr.cpp` from HEAD with recursive submodules; five CrispASR Dockerfiles `wget` release
  tarballs with no checksum (and `ark` pins v0.8.24 while the others pin v0.8.25).
  **Fix:** pin commits, verify checksums, unify the version.

### Dead code with real consequences

- **`webapp/app/asr_client.py` is unreachable** *(corroborated ×3)* — the `app/asr_client/` package
  shadows the 203-line module at import time, and the module has already drifted (it lacks the
  confidence/`avg_logprob` handling the live package has). Anyone reading or patching it is editing
  nothing. **Fix:** delete the file.

- **`approach-a/app.py` is a dead 1,104-line Flask server** *(corroborated ×2)* — superseded by
  `polyschnack_service` (the Dockerfile runs `server.py`), but still `COPY`d into the image, keeping
  `flask` + `waitress` and ~985 lines of unused templates in the build. **Fix:** delete it and the four
  unrun root scripts — about 2,310 lines and two dependencies.

### Process

- **`CONTRIBUTING.md` mandates ruff and mypy that do not exist** — `CONTRIBUTING.md:104`. Neither tool
  is a dependency, has a config, or runs in CI; there is no pre-commit or editorconfig anywhere. This
  is the root cause of most of the uniformity findings below. **Fix:** add ruff + mypy as dev
  dependencies with configs and a CI gate, or delete the claim from the contributing guide.

- **`process_recording` calls `run_llm_enhance` twice** — `webapp/app/service.py:904` and `:926`.
  A real behavioural bug found by the simplicity pass: with `llm_endpoint_id` set, enhancement runs
  twice — double latency and double token spend. **Fix:** remove the duplicate call.

## P2 — Medium

Correctness, hardening and consistency work. Grouped by reporting area, most severe first within each.


- **Upload reads the entire request body into memory before the size check** — `webapp/app/routers/recordings.py:506` · _Security_  
  `raw = await file.read()` materialises the whole multipart part in RAM and only then compares its length against MAX_UPLOAD_SIZE_MB (default 1024 MB) — the 413 fires after the memory has already been consumed, so the limit does not limit anything. The ps-webapp container is capped at 4 GB; a handful of concurrent multi-gigabyte POSTs (no authentication, no rate limit) OOM-kills it, and the same body is then copied again by prepare_storage/ffmpeg. Two related problems in the same handler: the file is written to disk (line 541) BEFORE enforce_anon_limits runs (line 555), so a rejected over-quota upload still leaves a full-size orphan file in AUDIO_DIR, and the identical read-everything pattern exists in openai_proxy.create_transcription (line 126) and transcribe_range (Path(...).read_bytes(), line 1215).  
  **Fix:** Stream the upload to a temp file in bounded chunks and abort with 413 as soon as the running total exceeds the limit (also check the Content-Length header up front), enforce the anon quota before writing to AUDIO_DIR, and reject oversized bodies at the reverse proxy (client_max_body_size) as a second layer.
- **Recovery of orphaned audio is unauthenticated when OIDC is disabled** — `webapp/app/routers/recovery.py:39` · _Security_  
  _require_admin returns immediately when OIDC is off — which is the default configuration of compose.yml (the OIDC block is commented out). In that deployment any anonymous visitor can call GET /api/recovery/scan to enumerate every orphaned audio file in AUDIO_DIR (names, sizes, ages) and POST /api/recovery/restore to materialise any of them as a Recording with user_id=None. Because permissions.get_access_level grants 'read' to everyone for rows with user_id None, the restored audio and its transcript become readable by every visitor — turning other users' abandoned uploads (which the module docstring itself calls 'potenziell sensible Audiodaten') into public content. Restore is also an unbounded disk-doubling primitive (it copies the file) with no rate limit.  
  **Fix:** Mirror deps.require_admin: when OIDC is disabled, deny the route (403) instead of allowing it, or gate the whole router behind an explicit POLYSCHNACK_ENABLE_RECOVERY env flag intended for local development only; assign restored recordings to a real owner rather than user_id=None.
- **Unauthenticated pip install trigger at POST /api/models/vad/download** — `webapp/app/routers/models.py:290` · _Security_  
  The whole /api/models router has no dependencies and no admin gate. POST /api/models/vad/download spawns a background thread that runs `pip install silero-vad` with the interpreter's own privileges (the container runs as root) and then downloads a model from the network. Any unauthenticated caller can trigger installation of a third-party package into the running production container and repeatedly cause network fetches and CPU/disk churn; if PyPI or the package is compromised, an outsider — not an operator — chose the moment of installation. The sibling endpoints also expose an unauthenticated internal-topology map (/api/models/status and /services return the ASR/diar/aligner service URLs, device information and raw exception strings).  
  **Fix:** Put the download endpoints behind Depends(require_admin), and preferably remove runtime pip installation entirely — bake silero-vad into the image (the Dockerfile already installs the other dependencies) so the running container never needs a package manager.
- **WebDAV delivery target performs unvalidated authenticated SSRF** — `webapp/app/deliver.py:57` · _Security_  
  DeliveryTarget config accepts an arbitrary `url` that is later PUT to with the stored credentials and the transcript body; unlike the BYOK LLM endpoints (routers/llm_endpoints.py calls validate_llm_url) the targets router applies no URL validation at all. A user can therefore point a target at http://docker-proxy:2375/..., http://ps-pk-onnx:5092/... or 169.254.169.254 and have the server issue authenticated requests into the internal network, exfiltrating transcripts to an arbitrary host at the same time. Note that the targets router's require_authenticated gate is a no-op when OIDC is disabled (deps.py line 36), so in the default compose deployment any anonymous visitor can create such a target. The destination path is also built by concatenating rec.original_name (user-controlled, may contain '../') into the URL.  
  **Fix:** Run cfg['url'] through validate_llm_url when the target is created/updated and again immediately before delivery (DNS may have changed), disable redirects on the httpx call, and percent-encode / sanitise rec.original_name before putting it in the path.
- **All containers run as root and the webapp can drive the Docker daemon** — `webapp/Dockerfile:39` · _Security_  
  None of the images drop privileges: the webapp Dockerfile has no USER directive, and approach-a/Dockerfile creates a 'polyschnack' user and then explicitly documents 'Run as root so the model download volume works without permission issues' (line 48). The webapp additionally holds network access to docker-proxy with CONTAINERS=1 and POST=1, i.e. it can start/stop/restart containers and read their logs. Any code-execution or file-write bug in the webapp (see the yt-dlp argument-injection finding) therefore executes as root, can rewrite the bind-mounted ./DATA volume and the SQLite database, and can manipulate containers on the host. The optional backends also publish unauthenticated inference APIs directly on host ports 5092-5097 (compose.yml line 38, compose.backends.yml), so anyone who can reach the host bypasses the webapp's quota and paid-path gating entirely.  
  **Fix:** Add a non-root USER to each image (chown the mounted volumes in the entrypoint or via an init container), set read_only/ no-new-privileges / cap_drop: [ALL] in compose, bind the backend ports to 127.0.0.1 instead of 0.0.0.0, and set DOCKER_PROXY_TOKEN so the proxy is not reachable by anything else on the compose network.
- **No rate limiting: unauthenticated endpoints create users, jobs and long-running subprocesses** — `webapp/app/anon_session.py:42` · _Security_  
  There is no rate limiting anywhere in the application. Every request without a session cookie inserts a new User row (unbounded DB growth from a trivial loop), each anonymous user then gets a fresh 500 MB disk quota and 100 MB upload allowance, and the URL import can occupy a yt-dlp subprocess for up to 600 s per call with a built-in automatic retry — all without authentication. The global queue cap (POLYSCHNACK_MAX_QUEUE_LEN=20) is shared across all users, so a single anonymous client can fill it and deny transcription to everyone else; peaks/preview generation spawns additional unbounded ffmpeg threads (_schedule_peaks) per upload. The retention sweep only reclaims anon users after POLYSCHNACK_ANON_RETENTION_MINUTES of inactivity, which does not help against an active attacker.  
  **Fix:** Add per-IP and per-identity rate limits (slowapi/limits or reverse-proxy level) on /api/recordings, /api/recordings/from-url, /v1/audio/transcriptions and /api/models/*; cap concurrent yt-dlp/ffmpeg subprocesses with a semaphore; make the queue limit per-user rather than global; and only materialise an anonymous User row when the request actually creates data.
- **_auto_migrate uses the Session after its context manager closed it; ALTER TABLEs are never committed** — `webapp/app/db.py:121` · _Code Smells_  
  The `with Session(engine) as session:` block ends at line 121 (after the ALTER TABLE loop), but lines 124-153 keep using `session` for the stale-processing UPDATE, the backend-rename UPDATEs and the final commit. The ALTER TABLEs themselves are never committed inside their block — they survive only because pysqlite runs DDL in autocommit; any change to the driver/isolation_level (e.g. `create_engine(..., isolation_level=...)`, a switch to sqlite3 with autocommit disabled, or a future Postgres move) silently rolls the schema migration back while init_db reports success. The follow-up UPDATEs likewise depend on SQLAlchemy silently re-opening a closed Session.  
  **Fix:** Put the whole migration inside one `with Session(engine) as session:` block and commit explicitly after the DDL loop; a test that asserts a migrated column survives a fresh engine/connection would have caught this.
- **_peaks_inflight guard is check-then-act and shared by two independent schedulers** — `webapp/app/routers/recordings.py:340` · _Code Smells_  
  _schedule_peaks does `if rec_id in _peaks_inflight: return` then `.add(...)` without a lock, and _backfill_peaks_batch (running in the peaks-backfill thread) adds/discards the same ids. Two failure modes: (a) GET /recordings and the transcribe endpoint can both pass the membership test for the same id and start two ffmpeg full decodes of the same 300 MB file — precisely the CPU/RAM collapse the comment says was fixed; (b) when the backfill thread and a _schedule_peaks thread work on the same id, whichever finishes first calls discard(), clearing the flag while the other decode is still running, so a third decode can start. Both threads then write the same row from different sessions (last writer wins).  
  **Fix:** Guard the set with a threading.Lock (or use a dict of futures), and have the backfill skip ids that are already inflight instead of discarding them unconditionally.
- **Public retention silently deletes admin-restored recordings an hour after recovery** — `webapp/app/db.py:56` · _Code Smells_  
  _purge_expired (run from init_db on every startup) deletes every Recording with user_id IS NULL older than PUBLIC_RETENTION_MINUTES (default 60) together with its file. recovery.recovery_restore deliberately creates restored orphans with user_id=None ('anonym — gehört niemandem, aber ist sichtbar'). An admin who recovers files after an incident loses them again — row and audio file — at the next restart occurring more than 60 minutes later, with no warning and no undo. The purge also has no guard against rows currently queued/processing.  
  **Fix:** Mark restored rows (e.g. source='restored') and exclude them from the purge, and skip rows whose status is queued/processing.
- **SMTP delivery has no timeout — a queue worker (and its endpoint slot) can hang forever** — `webapp/app/deliver.py:44` · _Code Smells_  
  smtplib.SMTP(host, port) is created without `timeout=`, so it inherits the global socket default (usually None = infinite). deliver() is called from process_recording inside the queue worker. A blackholed SMTP host (firewall DROP) parks the worker thread indefinitely; because the worker never releases the backend semaphore, that endpoint's capacity is permanently reduced and, with concurrency 1, the backend stops accepting jobs entirely. The stale-processing sweep will meanwhile mark the recording 'failed' even though the transcription actually succeeded.  
  **Fix:** Pass an explicit timeout (e.g. 30 s) to smtplib.SMTP and wrap delivery in its own try/except so a delivery failure cannot outlive the job.
- **vad._decode_to_wav runs ffmpeg without a timeout** — `webapp/app/vad.py:46` · _Code Smells_  
  subprocess.run(ffmpeg, input=audio_bytes, capture_output=True) has no timeout, unlike every other ffmpeg call in the codebase (audio_utils 300/600 s, peaks 900 s, service 120 s). A malformed container that makes ffmpeg spin (or a stalled pipe) hangs the queue worker forever with the recording stuck at progress 12 'vad'. The function also decodes the whole file into a float32 numpy array (4 bytes/sample → ~1.4 GB for a 6 h recording) and trim_silence_with_offset decodes it a second time.  
  **Fix:** Add a timeout and reuse the streaming/path-based decode approach from peaks.compute_peaks_path instead of materialising the whole waveform twice.
- **transcribe-range: deterministic crop filename collides across recordings; no range validation** — `webapp/app/routers/recordings.py:1220` · _Code Smells_  
  crop_path is derived from the source stem plus int(start)-int(end), so calling the endpoint twice with the same (or rounding-equal, e.g. 10.2 and 10.7) range creates a second Recording row pointing at the same file path, silently overwriting the first crop's audio. Deleting either row unlinks the shared file, leaving the other row with status done and a 410 on /audio. start_sec/end_sec are also unvalidated: end < start yields a negative `-t` for ffmpeg (trim_audio, service.py:1046, which additionally has no subprocess timeout), and the whole source file is read into RAM via read_bytes() before trimming.  
  **Fix:** Use a uuid4 filename like every other write path, validate 0 <= start < end <= duration, and let ffmpeg read the source by path instead of buffering it.
- **Frontend stops polling for 'queued' recordings — the card freezes until a manual reload** — `webapp/frontend/src/hooks.ts:28` · _Code Smells_  
  useRecordings only sets a refetchInterval when some recording has status === 'processing'; useStats only when stats.processing > 0. A recording that is enqueued behind another job gets status 'queued' (crud.set_queued), which matches neither predicate, so React Query stops polling entirely. If nothing else is processing in the user's own list — the normal case for a second user whose job waits behind a foreign job — the card shows 'queued' forever, including after the transcription has long finished. QueueWatcher polls separately but only renders the anonymised job list, not the card.  
  **Fix:** Poll while status is 'queued' or 'processing' (and mirror that in useStats).
- **Destructive endpoints ignore in-flight queue jobs** — `webapp/app/routers/recordings.py:744` · _Code Smells_  
  merge_recordings deletes the source rows and unlinks their audio files, delete_recording_endpoint does the same for a single row, and retention.sweep deletes an anon user's recordings — none of them consult queue_manager.active_jobs_for / the job map. If the recording is currently being transcribed, the worker's audio_path.read_bytes() raises mid-job (or, worse, after the ASR stage the update_result silently writes to a deleted id and returns None), leaving the queue slot occupied and the user with no feedback. Merging while a source is queued additionally leaves a phantom queue entry whose rec_id no longer exists.  
  **Fix:** Reject (409) or cancel the job when a recording is queued/processing, using the same guard as the admin endpoint-stop path (queue_manager.active_jobs_for).
- **Random per-process SESSION_SECRET orphans every anonymous user's recordings on restart** — `webapp/app/main.py:219` · _Code Smells_  
  When SESSION_SECRET is unset the app generates a fresh key at import time. Every anonymous identity lives in that signed cookie (anon_session.ensure_anonymous_user), and anonymous recordings are owned by the corresponding User row. After a restart (or with more than one uvicorn worker process, where each has its own key) the cookie no longer verifies, a brand-new anon user is created, and the previous recordings become invisible to their uploader — they remain on disk and in the DB until the retention sweep removes them. With multiple workers the identity flips per request, so uploads and transcribes land under different users and produce spurious 403s.  
  **Fix:** Fail fast (or persist a generated key to the data volume) when SESSION_SECRET is empty, and log a clear error rather than silently rotating identities.
- **approach-a service dependencies are entirely unpinned and installed as root with --break-system-packages** — `approach-a/requirements.txt:1` · _Supply Chain_  
  The ASR service image installs from requirements.txt where 12 of 14 entries are open-ended `>=` with no upper bound: onnx-asr[hub]>=0.10.0, fastapi>=0.115.0, uvicorn[standard]>=0.30.0, python-multipart>=0.0.9, silero-vad>=6.0.0, waitress>=3.0.0, flask>=3.0.0, openai>=1.0.0, typing_extensions>=4.0.0, psutil>=5.0.0, requests>=2.0.0, noisereduce>=3.0.0. Only onnxruntime-gpu==1.28.0 and numpy<2 are constrained. `openai>=1.0.0` and `requests>=2.0.0` in particular will happily absorb future major versions. approach-a/uv.lock exists but locks a *different* project (polyschnack-bench: gtts, jiwer, miniaudio — 21 packages) and never covers the service, so the deployed image has no lockfile at all. Dockerfile:35 installs with `pip install --no-cache-dir --break-system-packages` as root; a `polyschnack` user is created at line 26 but Dockerfile:48 explicitly declines to use it, so the container runs as root.  
  **Fix:** Generate a hash-pinned constraints file (`uv pip compile --generate-hashes`) for the service and install with `--require-hashes` into a venv rather than the system Python; then actually `USER polyschnack` and fix the model-volume ownership instead of staying root.
- **node:20-slim base image is past end-of-life** — `webapp/Dockerfile:4` · _Supply Chain_  
  The frontend build stage uses `node:20-slim`. Node.js 20 'Iron' reached end-of-life on 2026-04-30 (confirmed against the Node.js release schedule) and no longer receives security patches, so the base layer accumulates unpatched OpenSSL/V8/npm issues. The same version is used in CI (.gitlab-ci.yml:49 `image: node:20-slim`, .github/workflows/ci.yml:45 `node-version: 20`). This is a build-time toolchain rather than a runtime image, which limits exposure, but the npm client and its TLS stack in that image are what fetch 318 packages from the registry.  
  **Fix:** Move to node:22-slim (supported until 2027-04-30) or node:24-slim across the Dockerfile and both CI configs, pinned by digest.
- **Base images pinned by tag only, with `latest` in several places** — `compose.yml:17` · _Supply Chain_  
  No image anywhere in the repo is pinned by digest. `nvidia/cuda:12.8.0-devel-ubuntu24.04` and `-runtime-ubuntu24.04` (all nine Dockerfiles), `ghcr.io/astral-sh/uv:python3.12-bookworm-slim` (webapp/Dockerfile:20), `python:3.12-slim`/`3.11-slim`/`3.13-slim` and `${HARBOR_REGISTRY}/public/ci-tools` (.gitlab-ci.yml) are all mutable tags. Explicit `latest` appears at compose.yml:17 (`tecnativa/docker-socket-proxy:latest`, a container that proxies the host Docker socket), .gitlab-ci.yml:242 (`alpine:latest` for the mirror job that handles the GitHub PAT), polyschnack-manage.sh:227 (bare `alpine`), and every service entry in compose.yml / compose.gpu.yml / compose.backends.yml / compose.benchmark.yml (`…/polyschnack-asr*:latest`). ci_smart_build.sh pushes both `:latest` and `:${CI_COMMIT_SHORT_SHA}`, but only `:latest` is what deployments consume, so a rollback or a pinned deploy is impossible.  
  **Fix:** Pin third-party bases by `name:tag@sha256:…` (Renovate/Dependabot can bump them), and have compose consume `${POLYSCHNACK_TAG:-latest}` so a deployment can be nailed to a commit SHA tag.
- **Webapp lockfile drags in torch plus the full NVIDIA CUDA wheel stack** — `webapp/uv.lock:1` · _Supply Chain_  
  The Dockerfile comment at webapp/Dockerfile:29-31 claims 'Kein CUDA-torch mehr in der Webapp … Die Webapp bleibt CPU-only (~2,5-3 GB kleiner)', but the resolved lock contains torch@2.13.0, torchaudio@2.11.0, triton@3.7.1 and eighteen nvidia-*/cuda-* wheels (nvidia-cublas@13.1.1.3, nvidia-cudnn-cu13@9.20.0.48, nvidia-nccl-cu13@2.29.7, cuda-toolkit@13.0.3.0, …). They arrive transitively through `silero-vad>=6.0.0`, which is used only for voice-activity detection.
